## Gate 003 — Numerical Determinism / Equivalence Gate (QUEUED, NOT STARTED)
Explicitly held separate per Jack's direction — implementation-level,
affects replay equivalence, must not mix with lineage findings above.

**Gate objective (Jack's formulation, recorded verbatim):** Determine
whether the numerical contract produces the same deterministic result
for the same defined input across implementations, platforms, and
replay, and identify any unspecified behavior that prevents that claim.
This is a bit-/value-equivalence standard, not merely "confirm the
implementation uses fixed point."

**Equivalence standard:** Given identical canonical inputs and identical
declared contract/version, does every conforming implementation produce
the identical canonical numerical result and serialized representation?
Requires tracing: input → normalization → arithmetic operation →
rounding → fixed-point result → serialization → hash, with an
independently reproducible expected result — more than ordinary unit
tests.

**Critical issue to investigate first:** whether `fp()` is actually
fully specified. `FP_SCALE=10,000` + `ROUND_HALF_EVEN` does not fully
specify `sqrt()` — two implementations can both claim ROUND_HALF_EVEN
and still diverge via different approximation algorithms, different
intermediate precision, or rounding after every operation vs. only at
the end.

**Evidence questions and required evidence per item:**

| # | Question | Required evidence |
|---|---|---|
| 1 | sqrt() algorithm and rounding | Exact algorithm/library, input/output representation, rounding mode, intermediate precision |
| 2 | Division semantics | Integer vs floating division, quotient/remainder behavior, rounding/truncation rules, zero-divisor behavior |
| 3 | Intermediate precision | Precision between operations; whether values leave fixed-point representation |
| 4 | Overflow/underflow | Bounds, detection, saturation/wrapping/exception behavior, deterministic error behavior |
| 5 | Negative/zero handling | Exact semantics for negative operands, -0, zero denominators, negative square roots |
| 6 | ROUND_HALF_EVEN application points | Exactly which operations round, when, whether intermediate results round |
| 7 | FP_SCALE = 10,000 enforcement | Where scale is defined, enforced, validated; whether alternate scales can enter the system |
| 8 | Fixed-point serialization | Canonical integer representation, JSON representation, sign handling, scale metadata, canonicalization |
| 9 | Cross-platform equivalence | Evidence that identical inputs produce identical outputs across supported architectures/runtimes |
| 10 | Python/native authority | Whether Python arithmetic, a native library, platform math, or an explicit PH6 algorithm is authoritative |
| 11 | Test vectors | Known inputs → exact expected outputs, including boundary and pathological cases |

**Per-item classification taxonomy** — every element above must be
classified as one of: EXPLICITLY SPECIFIED / IMPLEMENTED / TESTED /
REPLAY-VERIFIED / CROSS-PLATFORM VERIFIED / UNSPECIFIED / CONFLICTING /
UNVERIFIABLE. The final determination is evidence-based, not inferred —
"we have a value for FP_SCALE" does not by itself justify classifying
sqrt() rounding as SPECIFIED.

**Execution stance (Jack's direction):** run this as an evidence
request against the existing PH6 corpus, not as drafting a new numerical
specification before inspecting existing source.
